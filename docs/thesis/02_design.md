# 3. Απαιτήσεις, δεδομένα και μεθοδολογία
## 3.1 Μεθοδολογική προσέγγιση
Η εργασία εξετάζει ένα λογισμικό ως τεχνούργημα εφαρμοσμένης Πληροφορικής. Η μέθοδος περιλαμβάνει διατύπωση απαιτήσεων, αντιστοίχιση απαιτήσεων σε διαδρομές κώδικα, εξέταση συμβολαίων δεδομένων και επαλήθευση με αυτοματοποιημένες δοκιμές. Το σύνολο των αποθηκευμένων μοντέλων αντιμετωπίζεται ως παρατηρούμενο αποτέλεσμα συγκεκριμένης εκτέλεσης, όχι ως νέο πείραμα που επαναλήφθηκε για τη συγγραφή. Κατά την τεκμηρίωση δεν εκτελέστηκε παραγωγική επανεκπαίδευση και δεν μεταβλήθηκαν δεδομένα χρηστών.

Η προσέγγιση συνδυάζει στατική και δυναμική εξέταση. Η στατική εξέταση ακολουθεί τις κλήσεις από το main.go προς τους handlers, τις ενέργειες χρήστη, τα pipelines και τους clients. Η δυναμική εξέταση επαναλαμβάνει τα διαθέσιμα unit και integration-style tests που χρησιμοποιούν ελεγχόμενα δεδομένα. Όπου μια δοκιμή προσομοιώνει το HTTP ή τη βάση, αυτό δηλώνεται ρητά. Η επιτυχία της δεν μετατρέπεται σε ισχυρισμό ότι πραγματοποιήθηκε πραγματική συναλλαγή σε ζωντανό περιβάλλον.

Αντικείμενο της μελέτης είναι το λειτουργικό υποσύνολο κατοικιών. Το Worker διαθέτει γενικότερες ρυθμίσεις για κτίρια, οικόπεδα, αγροτεμάχια και επαγγελματικά ακίνητα, αλλά η κύρια εφαρμογή φορτώνει δύο Phase2 μοντέλα κατοικιών: ένα για sell και ένα για rent. Η ύπαρξη παραγόμενων αρχείων άλλων κατηγοριών δεν αποδεικνύει ότι οι αντίστοιχες διαδρομές είναι προσβάσιμες από την τρέχουσα διεπαφή.

## 3.2 Λειτουργικές απαιτήσεις και αποδοχή
Η αναζήτηση πρέπει να είναι ελεγχόμενη ως προς το πλήθος αποτελεσμάτων και να διατηρεί το πλαίσιο του χρήστη. Το Browse επιστρέφει έως είκοσι περιλήψεις και πληροφορία ύπαρξης επόμενης σελίδας. Η επιλογή μιας περίληψης ανοίγει λεπτομέρειες χωρίς να χάνει τα εφαρμοσμένα φίλτρα. Η απαίτηση δεν περιλαμβάνει αυτόματη φόρτωση όλης της βάσης ή ακριβές συνολικό πλήθος αποτελεσμάτων.

Το προσωπικό χαρτοφυλάκιο έχει διαφορετικό όριο πρόσβασης από τη δημόσια ως προς τους συνδεδεμένους χρήστες αγορά. Η ιδιόκτητη προβολή πρέπει να επιβεβαιώνει τη σχέση χρήστη και ακινήτου. Η διαγραφή από το χαρτοφυλάκιο πρέπει να αφαιρεί μόνο αυτή τη σχέση. Η ίδια η εγγραφή και τα παράγωγα δεδομένα δεν διαγράφονται. Αυτή η διάκριση προφυλάσσει τις κοινές εγγραφές, αλλά σημαίνει επίσης ότι η ενέργεια δεν ισοδυναμεί με πλήρη διαγραφή προσωπικών δεδομένων.

Η εισαγωγή κατοικίας πρέπει να επιτρέπει απουσία ζητούμενης τιμής. Η πρόβλεψη στηρίζεται στα χαρακτηριστικά και δεν απαιτεί την τιμή ως είσοδο. Αντίθετα, το κατάλοιπο και οι όροι κατάταξης που συγκρίνουν asking και estimate απαιτούν θετική asking. Η σωστή αναπαράσταση της απουσίας είναι NULL ή nil και όχι μηδέν. Ένα μηδενικό ποσό θα μπορούσε να προκαλέσει διαίρεση με μηδέν ή να εμφανίσει πλασματική ευκαιρία.

## 3.3 Ποιότητα και μη λειτουργικές απαιτήσεις
Η συνέπεια έχει πολλές διαστάσεις. Σημασιολογική συνέπεια σημαίνει ότι το f20 είναι Elevator παντού. Αριθμητική συνέπεια σημαίνει ότι η πρόβλεψη ONNX συμφωνεί μέσα σε ανοχή με τη native πρόβλεψη. Συνέπεια ανάγνωσης σημαίνει ότι μια λεπτομερής προβολή δεν συνδυάζει αυθαίρετα γραμμές από δύο διαφορετικά snapshots της βάσης. Συνέπεια δημοσίευσης σημαίνει ότι το ενεργό μοντέλο και τα συνοδευτικά δεδομένα μπορούν να αντιστοιχιστούν στην ίδια γενιά.

Οι τέσσερις διαστάσεις δεν καλύπτονται από έναν μόνο mutex ή ένα hash. Ο mutex προστατεύει κοινή μνήμη εντός διεργασίας. Το hash ελέγχει ταυτότητα bytes. Η συναλλαγή PostgreSQL προστατεύει συγκεκριμένες εντολές βάσης. Η αναγνωσιμότητα των logs βοηθά στη διάγνωση. Καμία από αυτές τις τεχνικές δεν αποτελεί από μόνη της πλήρη εγγύηση ορθότητας κατανεμημένης δημοσίευσης.

Η απλότητα του κώδικα αποτελεί επίσης απαίτηση, επειδή το έργο πρέπει να μπορεί να συντηρηθεί και να εξηγηθεί. Η χρήση μικρών κοινών helpers για την ανάγνωση λεπτομερειών αποτρέπει διπλή υλοποίηση owner και browse λογικής. Αντίστοιχα, η κεντρική λίστα χαρακτηριστικών μειώνει τον κίνδυνο σιωπηρής απόκλισης. Όμως η απλότητα δεν σημαίνει κατάργηση κρίσιμων ελέγχων: ένας έλεγχος πλήθους χαρακτηριστικών ή δικαιώματος ιδιοκτησίας προστατεύει το νόημα της λειτουργίας.

## 3.4 Προέλευση, πληθυσμός και περιορισμοί δεδομένων
Το schema_dump.sql είναι σχήμα και όχι πλήρες dataset. Δεν επαρκεί για αναπαραγωγή των αριθμητικών αποτελεσμάτων. Τα manifests των ενεργών μοντέλων αναφέρουν 123.449 γραμμές πωλήσεων και 39.781 γραμμές μισθώσεων. Οι αριθμοί αυτοί είναι οι πληθυσμοί της συγκεκριμένης εκπαιδευτικής δημοσίευσης και όχι εγγύηση για το σημερινό πλήθος της βάσης. Νέες καταχωρίσεις ή διαγραφές σχέσεων μπορούν να αλλάξουν άλλες μετρήσεις χωρίς νέα εκπαίδευση.

Οι εντολές επιλογής για εκπαίδευση απαιτούν έγκυρη θετική ζητούμενη τιμή και τα απαραίτητα χαρακτηριστικά. Η επιλογή αυτή δημιουργεί υποπληθυσμό. Κατοικίες χωρίς asking μπορούν να εκτιμηθούν online αλλά δεν συμμετέχουν στην επιβλεπόμενη εκπαίδευση. Δεν υπάρχει στο εξεταζόμενο bundle πλήρης τεκμηρίωση αρχικής συλλογής, άδειας επαναχρησιμοποίησης, συχνότητας ενημέρωσης, αποδιπλοποίησης και χρονικής κάλυψης. Αυτά παραμένουν προϋποθέσεις για δημόσια διάθεση και ισχυρή επιστημονική αναπαραγωγή.

Το dataset δεν πρέπει να περιγραφεί ως τυχαίο αντιπροσωπευτικό δείγμα όλων των ελληνικών ακινήτων. Τα χαρακτηριστικά μιας βάσης αγγελιών εξαρτώνται από τους διαθέσιμους παρόχους, την ψηφιακή παρουσία, την περιοχή και τον χρόνο παρατήρησης. Ελλείψεις ή πολλαπλές αγγελίες του ίδιου ακινήτου μπορούν να επηρεάσουν την εκπαίδευση και την επικύρωση. Η παρούσα μελέτη δεν εισάγει αυθαίρετους ισχυρισμούς ότι αυτά τα προβλήματα έχουν λυθεί.

# 4. Αρχιτεκτονική, σκελετός και αρχικοποίηση
## 4.1 Διάσπαση σε υποσυστήματα
Το σύστημα αποτελείται από τέσσερις κύριες εκτελούμενες υπηρεσίες στο περιβάλλον ανάπτυξης: τον Vite server της διεπαφής, τη Go υπηρεσία HTTP, την PostgreSQL/PostGIS και την Python υπηρεσία FastAPI. Ο καθολικός trainer είναι πέμπτη, προσωρινή διεργασία, που ξεκινά από τη Go όταν απαιτείται εκπαίδευση. Δεν πρέπει να συγχέεται με τον ήδη ενεργό Python server. Το ότι και οι δύο γράφονται σε Python δεν συνεπάγεται κοινή μνήμη ή αυτόματη ανταλλαγή αντικειμένων.

Η διεπαφή επικοινωνεί μόνο με τη Go μέσω των routes /register, /User και /analysis. Στην ανάπτυξη οι κλήσεις περνούν από το Vite proxy προς localhost:8080. Η Go εκτελεί SQL, ONNX inference και HTTP κλήσεις προς την Python. Η Python δεν αποτελεί απευθείας browser API για τις κανονικές ενέργειες χρήστη. Αυτή η διάταξη διατηρεί το σημείο αυθεντικοποίησης στη Go, χωρίς όμως να εξαλείφει την ανάγκη προστασίας της εσωτερικής θύρας Python.

## 4.4 Εκκίνηση Go και διαθέσιμα μοντέλα
Η WarmUpApplication ανοίγει την πρόσβαση στη βάση μέσω InitDB1 και αποθηκεύει το pool στον Calculator. Έπειτα καλεί WarmUpTrees. Η τελευταία ορίζει τη διαδρομή της native βιβλιοθήκης onnxengine.dll, αρχικοποιεί το ONNX Runtime και ελέγχει αν υπάρχουν τα δύο σταθερά ONNX αρχεία. Αν υπάρχουν, φορτώνονται. Αν λείπουν, η τρέχουσα υλοποίηση οδηγείται σε εκπαίδευση. Η αυτόματη αυτή διαδρομή είναι σημαντική λειτουργική προειδοποίηση: η εκκίνηση δεν είναι πάντα μόνο read-only φόρτωση.

@source Ptixiaki/main.go|421|464

Το context.Background δεν συνδέεται με ένα συγκεκριμένο αίτημα. Χρησιμοποιείται ως ρίζα για εργασίες αρχικοποίησης. Αντίθετα, όταν ένας handler λαμβάνει r.Context, οι επιμέρους ενέργειες μπορούν να πληροφορηθούν ότι ο πελάτης ακύρωσε το αίτημα. Η εκκίνηση από ξεχωριστά terminals είναι ο πραγματικός μηχανισμός του τρέχοντος περιβάλλοντος. Ένας μελλοντικός launcher θα ήταν εξωτερικός διαχειριστής διεργασιών, όχι ιδιότητα του μοντέλου.

## 4.6 Mutex, παράλληλα αιτήματα και αλλαγή γενιάς
Ένας RWMutex επιτρέπει πολλούς αναγνώστες ταυτόχρονα, αλλά αποκλείει τη λειτουργία εγγραφής όσο υπάρχουν ενεργοί αναγνώστες (Go Authors, χ.χ.-δ). Στο AddPropertyHandler η RLock κρατά τη συγκεκριμένη γενιά μοντέλου ζωντανή μέχρι να ολοκληρωθεί η ροή. Η publishTrees αποκτά την αποκλειστική Lock προτού αλλάξει pointers και καταστρέψει τα παλιά sessions. Χωρίς αυτόν τον συντονισμό ένα αίτημα θα μπορούσε να χρησιμοποιεί native μνήμη που έχει ήδη ελευθερωθεί.

Η κοινή κλειδαριά δεν παγώνει ολόκληρο τον HTTP server. Ανεξάρτητα endpoints μπορούν να εκτελούνται παράλληλα, ενώ περισσότερες προσθήκες μπορούν να κρατούν RLock. Υπάρχει όμως και δεύτερο mutex μέσα σε κάθε ModelPredictor: προστατεύει το γράψιμο στο κοινό InputData, την εκτέλεση και την ανάγνωση του OutputData. Στον ίδιο predictor οι ίδιες οι προβλέψεις σειριοποιούνται. Sell και rent έχουν διαφορετικά αντικείμενα και διαφορετικά εσωτερικά locks.

Αυτή η διάταξη είναι απλή και κατανοητή για το μέγεθος του έργου. Σε υψηλό φορτίο θα μπορούσαν να εξεταστούν ανεξάρτητα tensors ανά αίτημα ή pool sessions, μετά από μέτρηση. Η αλλαγή δεν πρέπει να γίνει μόνο με αφαίρεση του mutex, επειδή δύο goroutines θα μπορούσαν να αναμείξουν χαρακτηριστικά διαφορετικών ακινήτων. Προτεραιότητα είναι η ορθή ιδιοκτησία της μνήμης και κατόπιν η βελτιστοποίηση της παραλληλίας.

## 4.7 Εκκίνηση Python και ml_shared
Ο Python server κατασκευάζει ExplainModelRegistry κατά την εισαγωγή του module. Στο lifespan επιχειρεί να φορτώσει sell και rent. Αν λείπει έγκυρο ζεύγος UBJ/manifest, καταγράφει προειδοποίηση και η υπηρεσία μπορεί να συνεχίσει, ενώ η εξήγηση παραμένει μη διαθέσιμη. Η κατάσταση αυτή διαφέρει από την εκκίνηση Go, όπου η αποτυχία προθέρμανσης οδηγεί σε τερματισμό.

Το ml_shared είναι πακέτο κοινών Python συναρτήσεων. Περιέχει τη λίστα χαρακτηριστικών, τη δημιουργία/επικύρωση manifest, τη φόρτωση native μοντέλου, τους ατομικούς χειρισμούς αρχείων και την αριθμητική ανοχή SHAP. Οι παλιοί κατάλογοι .gocache και .cache περιείχαν βοηθητικά δεδομένα εργαλείων και αφαιρούνται από το bundle χωρίς να επαναδημιουργούνται. Το Go build cache και τα προσωρινά development executables/logs παραμένουν εκτός του bundle, κανονικά στις διαδρομές `%LOCALAPPDATA%\go-build` και `%TEMP%\ptixiaki-dev` αντίστοιχα. Για τον λόγο αυτό η τεκμηρίωση διαχωρίζει τις διαδρομές κατασκευής από τις διαδρομές των ενεργών artifacts.
